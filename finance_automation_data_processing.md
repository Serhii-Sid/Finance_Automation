# 📘 Специфікація обробки даних та архітектури (Finance Automation Passport)

Цей документ є офіційним регламентом та технічним паспортом обробки даних у системі **Finance Automation**. Він описує архітектурні принципи імпорту виписок, стандартизації, дедуплікації, логіку розпізнавання внутрішніх переказів та формування Excel-звітів.

---

## Розділ 1. Загальна структура проєкту та налаштування файлового простору

Система функціонує за модульним принципом з чітким розділенням відповідальності:

- **`parsers/`**: Спеціалізовані банківські парсери для зчитування виписок у форматах PDF та Excel.
- **`input_data/`**: Директорія для розміщення сирих банківських файлів виписок.
- **`output/`**: Директорія зберігання згенерованих версій підсумкового звіту (`Total_Ledger.xlsx`).
- **`config.py`**: Глобальні словники карток (`CARDS_DICTIONARY`), ключові слова категорій (`CATEGORIES_KEYWORDS`), коди MCC (`MCC_MAP`) та назви колонок.
- **`src/data_manager.py`**: Модуль завантаження, стандартизації колонок, очищення та інкрементного дедуплікованого злиття.
- **`src/finance_logic.py`**: Модуль бізнес-логіки обробки кредитних лімітів, MCC-мапінгу, алгоритму спарювання близнюків (Twins) та динамічного розщеплення комісій.
- **`src/report_engine.py`**: Двигун побудови щоденного дашборду (`Daily_Dashboard`), підготовки аналітичних вкладок та openpyxl-стилізації.

---

## Розділ 2. Модуль банківських парсерів (Raw Ingestion)

Кожен парсер успадковує клас `BaseParser` та приводить сирі банківські дані до єдиної схеми колонок:
- `Дата`: дата та час операції.
- `Сума`: числове значення (від'ємне для витрат, додатне для доходів).
- `Картка`: назва або маска картки (наприклад, `Приват Sid Унів`, `Monobank Sid Чорна`).
- `Опис`: деталі операції від банку.
- `Категорія`: початкова категорія банку або `NA`.
- `Залишок`: баланс після операції.

## Розділ 3. Стандартизація даних та дедуплікація (Deduplication & Incremental Merge)

1. **Векторна генерація ID (`make_short_id_vectorized`)**:
   Для кожної транзакції обчислюється унікальний 8-значний MD5-хеш ідентифікатор на основі дати, картки та суми:
   $$\text{ID} = \text{MD5}(\text{Дата} + \text{"\_"} + \text{Картка} + \text{"\_"} + \text{Сума})[:8]$$

2. **Інкрементне злиття (`reconcile_and_merge`)**:
   При завантаженні нових банківських виписок система порівнює їх з існуючою базою `df_base` за ключем `[Дата, Картка, Опис, Сума]`. Дублікати відфільтровуються, а нові унікальні транзакції додаються до бази.

---

## Розділ 4. Двохетапна автокатегоризація ("Decision Funnel")

Категоризація здійснюється за принципом **"Keyword First"**:
1. **Первинний пошук за ключовими словами (`CATEGORIES_KEYWORDS`)**: опис нормалізується у нижній регістр та порівнюється з пріоритетним списком брендів і термінів.
2. **Резервний пошук за MCC-кодами (`MCC_MAP`) та банківською категорією**: застосовується, якщо ключові слова в описі відсутні.

## Розділ 5. Інтелектуальна обробка внутрішніх переказів ("Twins") та облік комісій

### 5.1 Принцип недоторканності сирих даних (Raw Data First)
Оригінальні транзакції-списання (наприклад, `-10 050.00 грн`) більше **НЕ розщеплюються** у первинній базі даних (`Total_Ledger` / вкладка `Transactions`). Вони зберігаються у первинному вигляді одним рядком з оригінальним 8-значним ID (наприклад, `'50461728'`). Це забезпечує абсолютну стабільність дедуплікатора при інкрементному злитті нових виписок.

### 5.2 Двохфазне спарювання "близнюків" у `detect_internal_transfers`
- **Фаза А (Точний збіг)**: Пошук двох транзакцій з однаковою сумою (різними знаками) між власними картками з точністю до 5 хвилин.
- **Фаза Б (М'який збіг з комісією)**: Пошук пари, де списання перевищує прихід у межах дозволеного допуску на комісію ($\le \max(\text{сума} \times 1\%, 100\text{ грн})$).
- Обидві транзакції маркуються відповідними категоріями (`переказ на власний рахунок` для витрати та `переказ з власного рахунку` для доходу), зберігаючи оригінальні суми та ID в базовому леджері.

### 5.3 Розщеплення "на льоту" під час генерації звітів (`expand_commission_splits_for_reports`)
Розщеплення на тіло переказу (`_main`) та комісію (`_comm`) відбувається динамічно "на льоту" за допомогою функції `expand_commission_splits_for_reports(df)` виключно під час формування аналітичних звітів (`Expenses` та `Daily_Dashboard`):
- **Основне тіло переказу**: сума `-10 000.00 грн`, категорія `'переказ на власний рахунок'`, ID `'50461728_main'`.
- **Комісія банку**: сума `-50.00 грн`, категорія `'інші витрати'`, ID `'50461728_comm'`.
- **Оригінальний прихід**: сума `+10 000.00 грн`, категорія `'переказ з власного рахунку'`, ID зберігається без змін.

## Розділ 6. Коригування кредитних лімітів та банківських балансів

Для карток із кредитними лімітами (наприклад, ПУМБ або Монобанк) виконується автоматичне коригування колонки `Залишок`, щоб враховувати лише власні кошти та розраховувати реальні чисті активи (Net Worth).

## Розділ 7. Модуль щоденної аналітики та генерації звітів (Report Engine)

### 7.1 Структура вкладок підсумкового Excel-файлу (`Total_Ledger.xlsx`)
1. **`Transactions`**: Повний реєстр сирих транзакцій БЕЗ розщеплення комісій (зберігши первинний вигляд і стабільність дедуплікації).
2. **`Expenses`**: Аналітичний реєстр витрат із динамічно розщепленими комісіями (`_main` та `_comm`).
3. **`Income`**: Аналітичний реєстр надходжень.
4. **`Daily_Dashboard`**: Зведений щоденний дашборд із місячними підсумками (`РАЗОМ`) та розрахунком накопичувального балансу.

### 7.2 openpyxl стилізація та візуальне маркування Twins-транзакцій
Під час відкриття та стилізації аркушів бібліотекою `openpyxl`:
- Алгоритм безпечно перевіряє стовпець ID транзакцій (`val = str(cell_with_id.value or "")`).
- Усі рядки на аналітичних вкладках (`Expenses`), ідентифікатори яких закінчуються на **`_main`** або **`_comm`**, автоматично підсвічуються м'яким **пастельно-жовтим кольором (`#FFF2CC`)**:
  ```python
  split_fill = PatternFill(start_color="FFF2CC", end_color="FFF2CC", fill_type="solid")
  ```
- Це забезпечує швидкий візуальний контроль та зручне сканування зв'язаних комісійних операцій у масиві даних.

## Розділ 8. Валідація знаку суми та Self-Cleaning Rules

Фінальна валідація перевіряє відповідність знаків суми та категорій:
- Дохідні категорії (`INCOME_CATEGORIES`) з від'ємною сумою примусово переводяться в `'інші витрати'`.
- Витратні категорії (`EXPENSES_CATEGORIES`) з додатною сумою переводяться в `'інші надходження'`.
- Категорії поза білим списком (`ALLOWED_CATEGORIES`) переводяться в відповідний fallback-клас.
